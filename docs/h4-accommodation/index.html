Recommended record structure

One H4 AccommodationRequest per student stay, with persons = 1 and one guest entry. Several requests share an AccommodationBatch when submitted together.

The batch is a convenience for creation, faculty review, and grouping. Each child owns its approval history, payer, payment, room, stay changes, and invoice. A batch summary shows mixed statuses without forcing everyone into one status.

Why this matches your suggestions

Student-wise rows stay consistent even when only one intern is approved, extends a stay, pays, or cancels. Creator and recommending faculty are distinct fields, so either grouping works.

Use stable batch and request IDs. Two batches from one creator remain separate submissions; grouping by creator can intentionally place them under one heading.

Confirmed by the user on 04 Oct 2026. Requester and recommending faculty emails must be institutional IIT Indore emails; interns may use external contact/payer emails. Every stage, its owner, and its result

Draft the batch — requester

Sign in with an allowed institutional account. Choose Intern, Unregistered student, or Other H4 category; specify a description for Other. Select the recommending faculty and add one or more people. Shared stay, purpose, and payer values can be copied to rows, then changed per student. Save a draft without sending notifications.

Separate creator identity from resident identity: “Created by Ananya” never means the intern is Ananya. An existing SMS student can be linked; an external student does not need a full SMS Student account.

Validate and submit — requester

Validate all rows, dates, emails, named faculty, payer choice, and required H4 fields before creating children. Show duplicate ID/email/stay warnings. Use a client idempotency key and an atomic create operation so retrying a batch cannot create duplicate students. Optional attachments use the existing storage service.

Student/staff submissions enter Pending Faculty Recommendation. All institutional users with the existing Academics role may create H4 requests. An Academics user submitting as the selected concerned faculty can explicitly submit and recommend; if they select another Academics user, the request goes to that selected faculty for recommendation.

Verify and recommend — concerned faculty

Show the full roster and each student’s dates, purpose, education, contact details, and who pays. Faculty may recommend selected students, return selected students with reasons, or decline them. One batch recommendation link can resolve several child records; actions and versions are recorded per child.

Faculty eligibility comes from existing User records with role = Academics and an IIT Indore institutional email. Every Academics user is eligible, regardless of sub-role. The faculty selector lists those users and stores the selected user ID. Only the selected concerned faculty can recommend the request. Recommendation links are scoped to that user and recheck their current eligibility when used.

Check capacity and recommend — CW Office

See date-aware room conflicts and current student allocations across hostel inventory. Zero empty guest rooms does not prevent H4 recommendation. CW Office records a feasibility note, proposed hostel, and any anticipated occupancy override; approval does not promise a specific room.

Recommended requests enter Pending CW Approval. A requested correction returns to the creator with a reason. An unchanged faculty recommendation remains valid; changes to student identity, dates, reason, faculty, or payer require a fresh recommendation.

Approve — Chief Warden

Approve or reject per student, with the faculty verification and CW Office recommendation visible. Return for correction when revision is allowed. Store actor, time, version, and reason. Default H4 policy requires an explicit approval; use reminders/escalations instead of inheriting the existing 24-hour auto-approval.

Issue the offer — CW Office

Set accommodation price and any configured tax, allot a hostel, set mess to With / Without, and confirm the verified billing party. Amounts become an immutable offer snapshot; the simulation’s amounts are illustrative, not an institute tariff. Mess is a preference and coordination flag, not a food line on the accommodation invoice.

Email stay information to each intern, the creator, and the recommending faculty as appropriate. Send payment instructions to the payer. No additional faculty approval round is introduced at this stage.

Pay and verify — named payer / accountant

An institutional faculty payer can use a scoped portal view; an external intern uses an expiring request-specific access link to view the offer and upload proof. Reuse UTR, payment date, and screenshot handling. The accountant accepts or rejects with a reason. The payer can correct and resubmit rejected evidence.

Default preserves current behavior: verified payment unlocks room assignment. “Pay later” may be offered, but it does not unlock rooms under the current code. An alternative “faculty undertaking allows arrival” would be a separately agreed H4 policy, not an assumed existing feature.

Assign a room — authorized hostel supervisor

Select hostel, enter unit where needed, enter room number, and check that it resolves to a real room. Review resident students, overlapping H2/legacy/H4 guests, room condition, and capacity warnings. Occupancy never hard-blocks H4. A supervisor who has authority for that hostel acknowledges current warnings and supplies an override note, then saves.

Recheck immediately before saving. An intern receives assignment details. Resident allocations are preserved. CW Office can re-allot a hostel; supervisor permissions do not silently expand to every hostel.

Operate the stay — supervisor / gate

Track per-student check-in and check-out. An extension or postponement goes to CW Office and reruns room conflict checks over the new interval; material changes invalidate approval as defined by policy. Extra amounts use the existing additional-payment mechanism. Room moves record before/after rooms and effective times.

Office cancellation ends reservations and retains payment history. Paid cancellations enter manual refund handling; the system never claims a refund occurred. No-shows are marked by staff or a documented policy, not invented from lack of a gate scan.

Close and invoice — accountant / scheduled worker

Separate reservation release from invoice readiness. End-of-stay releases only the H4 dated reservation even if a balance remains; it never reactivates a resident’s room. Generate the accommodation invoice once the stay is closed and relevant payments are settled. Bill to the payer snapshot, send to that payer, and provide access to the intern/creator according to scope.

Keep invoice numbering and PDF rendering infrastructure. Preserve issued invoices; corrections require an audited revised document or the accounting office’s process. No mess/food invoice is generated here.

Status design and negative paths

Reuse existing statuses where the meaning matches. Add a distinct H4 faculty recommendation stage; show “Returned for correction” to H4 users even if legacy storage retains Returned to Student.

Room policy / your occupancy requirement

Any room can be considered.
Conflicts stay visible.

Give staff a normal room entry form with a “Check room” action. The backend resolves the entered location and builds warnings from live records. A warning requires acknowledgement; it does not forbid H4 assignment.

Selection interaction

  1. Choose or search the allotted hostel. This is a short scoped list, not a dropdown of every room.
  2. Enter unit/block if that hostel uses units, then room number. Preserve letters and leading zeroes.
  3. Press Check room or Enter. Show canonical hostel / unit / room labels and capacity.
  4. Show all current warnings, relevant occupants, overlapping dates, and source request IDs.
  5. For conflicts, acknowledge the warnings and record why assignment is appropriate. Assigning remains available to authorized staff.
  6. Confirm. The API recomputes warnings and saves the reservation plus acknowledgement atomically.

Typed room numbers resolve to a real roomId. Unknown or ambiguous entries must be corrected; creating a room accidentally is outside this form. Never guess a unit from a concatenated room label.

Warnings versus invalid input

Advisory / overridable

Resident allocation, overlapping H2 guest, legacy visitor, H4 intern, nominal capacity exceeded, maintenance/storage/inactive state, or relevant hostel placement mismatch. Display all real room records in scope and explain each issue.

Input / permission errors

Room does not exist; unit is ambiguous; room is outside the actor’s hostel scope; dates are invalid; request is not ready for assignment; warning acknowledgement is missing or stale. These are correctness checks, not occupancy restrictions.

Default recommendation: all occupancy conflicts can be overridden by the authorized supervisor with a note. Any special maintenance or placement approval policy is a decision to agree, not a hidden hard-coded occupancy block.

Query owners remain separate: accommodation queries read accommodation records, visitor queries read legacy visitors, hostel queries read resident allocations and inventory. A composition service merges their results without importing their models into an app module.

Use actual stay windows

Normalize each stay into [effectiveStart, effectiveEnd) in Asia/Kolkata. Dates remain date-only for night-count calculation; clock times are stored separately. Early arrival and late departure extend the conflict window, not automatically the accommodation tariff.

overlap = existingStart < requestedEnd
       && existingEnd > requestedStart

Example: Guest A leaves 15 May at 11:00 IST.
         Intern B arrives 15 May at 11:00 IST → no overlap.
         Intern B arrives 15 May at 09:00 IST → two-hour overlap.

Exclude the current reservation on reassignment.
Cancelled / rejected reservations do not hold future dates.
Checked-out records stop at actual departure when confirmed.
Unknown dates or an overdue guest still checked in → uncertainty warning.

Historical records are normalized according to their original date contract; do not shift midnight-stored date-only values by accident. There is no reliable resident date overlap calculation until dated allocation/absence evidence is introduced. A future absence module is optional and must not erase a student’s allocation.

Separate temporary reservation ownership

Keep resident data untouched. Proposed AccommodationReservation records carry request ID, student/request reference, room ID, effective start/end, lifecycle, and assignment audit. H4 never calls holdRoomsForGuest or releaseRooms, never sets the room to Guest, and never inserts a resident RoomAllocation.

Mirror existing H2 and legacy bookings into the conflict response initially through adapters rather than duplicating their writes. H2 and legacy assignment/availability paths must also consult active H4 reservations before admitting a normal guest; normal-guest occupancy remains restrictive. This small integration prevents two separate pages from hiding each other’s commitments.

Closing, cancellation, extension, and room moves modify only H4 reservations. Existing H2 room status logic remains category-guarded. A later shared reservation migration for H2 can be a separate improvement.

Confirmation and concurrency

Preview the room

API returns canonical room identity, inventory details, structured warning codes, source IDs, effective intervals, checkedAt, and a short-lived conflict fingerprint scoped to the request version and actor.

Acknowledge what was shown

Submit resolved room ID, reservation interval, preview fingerprint, acknowledged warning codes, and override reason. Persist the server-produced warning snapshot with actor/time/reason; client warning text is not authoritative.

Recheck under a shared room lock

Serialize H4 and guest mutations by room, with ordered locks for multi-room moves, then read current conflicts and compare the fingerprint. If conditions changed, return refreshed warnings for review. Staff can still choose an intentional overlap after reviewing it.

Save atomically and idempotently

Write the reservation, request assignment projection, and override audit in one transaction. Optimistic request version plus an idempotency key prevents stale or duplicate actions. Lock TTL/ownership and error handling follow existing distributed lock conventions; database transactions protect the resulting multi-document write.

H2/legacy adapters must use the same lock/recheck convention when they mutate room commitments. Resident allocation operations can emit a supervisor alert when they intersect an H4 reservation; a broader resident-allocation policy is a separate decision.

Money, communications, and recoverability

Keep financial responsibility explicit

  • Faculty verifies intern/faculty payer choice before operations approval. The recommending faculty is the default faculty payer; a different faculty payer needs their explicit acceptance.
  • One invoice per student request in version one, even when the same faculty pays for many students. Creator grouping does not merge financial documents.
  • One combined transfer across students needs a separate payment receipt with an allocation ledger. Do not credit the full UTR amount independently to every child. Treat consolidated payments/invoices as a later agreed feature.
  • After offer issue, payer/amount changes require office reissue and renewed verification where material. After verified money or an issued invoice, use adjustment workflow; never silently rewrite billing history.
  • Any tax shown uses configured institute settings. This plan does not establish a rate or tax treatment.

Make delivery retryable

  • Faculty recommendation invitation; requester submission/decision/update; intern approved offer; payer payment request/rejection; supervisor readiness; room assignment/change; cancellation; invoice.
  • Queue notifications after durable state changes. Record recipient, template, event ID, delivery status and retry outcome; do not make email success the approval state.
  • Reuse the current email and file services. Expired faculty links can be reissued; old links are invalidated on revision, use or cancellation.
  • Reminders have type-aware recipients and are idempotent across scheduler instances. H4 never enters the H2 hard-coded timeout sweep accidentally.
  • Exports and daily arrival summaries distinguish H2/H4 and are hostel-scoped. A failed invoice PDF upload can be retried with the same invoice number.
